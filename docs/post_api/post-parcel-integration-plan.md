# 우체국 계약소포 접수·운송장 출력 연동 계획서

작성: 2026-08-18
대상: `easy-fulfill` 데스크톱 GUI

## 1. 목적

현재 주문을 수동으로 우체국 계약고객전용시스템에 접수하고, 운송장번호를 받은 뒤 네이버에 발송처리하는 흐름에서 다음 구간을 자동화한다.

```text
주문 선택
  → 우체국 계약소포 OpenAPI 접수
  → 소포신청 결과 재조회 및 등기번호 저장
  → 계약고객 시스템의 신규출력 운송장 일괄 인쇄
  → 네이버 발송처리
```

접수와 실제 인쇄는 각각 되돌리기 어렵거나 외부 상태를 바꾸므로, 각 단계를 독립적으로 검증한 뒤 순차적으로 연결한다.

## 2. 범위

### 포함

- 일반 계약소포(`reqType=1`)의 단건·다건 접수
- SEED128 암호화를 사용한 우체국 OpenAPI 호출
- 접수 성공 XML의 소포신청번호·예약번호·등기번호 저장
- 접수 결과 재조회 및 API 취소 지원
- `신규출력` 대상 운송장을 이용한 일괄 인쇄 자동화
- 우체국 등기번호를 기존 네이버 발송처리 대상에 연결
- 접수·인쇄·네이버 발송의 단계별 결과와 오류 기록

### 제외

- 반품소포, 맞교환, 다량등기, EMS 연동
- 우체국 API 키 발급·계약 변경·프린터 드라이버 설치
- 라벨 디자인·운송장 양식 자체 제작
- 실제 배송 완료 여부의 자동 판정

반품소포는 일반소포 흐름과 필수 필드 및 취소 조건이 달라, 일반소포 실운영 검증 후 별도 범위로 다룬다.

## 4. 설계 원칙

1. **접수와 인쇄를 분리한다.** API 접수 성공만으로 실제 용지 출력이나 네이버 발송을 완료로 표시하지 않는다.
2. **등기번호를 기준으로 연결한다.** 우체국에서 부여한 `regiNo`가 주문·출력·네이버 발송의 공통 키다.
3. **외부 쓰기 전에 재확인한다.** 접수 후에는 `GetResInfo`로, 네이버 발송 전에는 접수·인쇄 상태로 확인한다.
4. **중복 접수를 막는다.** 하나의 상품주문번호 또는 내부 주문 접수 키에 활성 우체국 접수 이력이 있으면 기본적으로 재접수를 차단한다.
5. **신규출력 목록을 무조건 전체 인쇄하지 않는다.** 이번 실행에서 접수된 등기번호 목록과 신규출력 조회 결과를 비교한다.
6. **물리적 출력은 별도 증거다.** 우체국의 출력여부 변경, Windows 인쇄 명령 전달, 실제 프린터 출력은 다른 상태로 기록한다.
7. **비밀값은 기존 비공개 공유 `설정` 탭에서만 관리한다.** 사용자 지시에 따라 전 직원이 사용하는 접근 제어된 `설정` 탭에 저장하되, 코드·Git·문서·콘솔 로그·일반 업무 시트에는 넣지 않는다.

## 5. 데이터 매핑

### 5.1 기준 입력: 「송장·발송 생성」의 송장 행

우체국 API 접수의 기준 입력은 사용자가 메인 화면 「송장·발송 생성」에서 생성하는 기존 우체국 접수 양식으로 한다. 실접수 구현에서는 그 파일을 만드는 `orders.invoice.build_invoice_rows()`의 송장 행을 API 요청 입력으로 재사용한다. 현재 테스트 접수 메뉴는 안전한 1건 검증을 위해 기존 송장 `.xlsx` 파일을 선택받아 같은 변환기를 호출하며, 기존 엑셀 생성은 계속 유지해 수동 접수 폴백으로 쓴다.

이 경로는 `주문번호`, `수취인명`, `우편번호`, `수취인 주소`, 수취인 전화·이동통신, `상품명`, `상품모델`, `배송메세지`를 주문별로 제공한다. `고객주문처명`은 현재 빈 값이며, `InsertOrder` 테스트에서 공란도 허용됨을 확인했다.

퀵 수동 엑셀도 동일한 11개 열 구조를 사용하므로 같은 변환기를 재사용한다. 단, 수동 입력은 주문번호가 비어 있을 수 있어 API 접수 전에 프로그램이 고유 주문번호를 생성해야 한다.

### 5.2 우체국 접수 필수값

| 우체국 필드 | 값의 출처 | 비고 |
| --- | --- | --- |
| `custNo` | 로컬 계약 설정 | 고객번호 |
| `apprNo` | 로컬 계약 설정 | 계약 승인번호 |
| `payType` | 로컬 계약 설정 또는 명시 선택 | 일반/수취인 부담 |
| `reqType` | 고정 `1` | 일반소포 |
| `officeSer` | 로컬 계약 설정 | 공급지 코드 |
| `microYn` | 주문/기본 설정 | 초소형 여부 |
| `orderNo` | 내부 주문 식별자 | API 접수 중복 방지에도 사용 |
| `ordCompNm` | 송장 행의 고객주문처명 | 공란 허용 확인 |
| `recNm` | 주문 수취인명 | 필수 |
| `recZip` | 주문 우편번호 | 필수 |
| `recAddr1`, `recAddr2` | 주문 배송지 | 필수 |
| `recTel` 또는 `recMob` | 주문 수취인 연락처 | 둘 중 하나 이상 필요 |
| `contCd` | 기본 설정 또는 상품 분류 | 주요 내용품 코드 |
| `goodsNm` | 주문 상품명 | 필수 |

`weight`, `volume`, `packngMtrCd`, `qty`, `goodsCd`, `goodsMdl`, `goodsSize`, `goodsColor`, `delivMsg`, `insuYn`, `insuAmt` 등은 주문 데이터와 운영 기본값을 확인한 뒤 추가한다. 중량과 부피는 정수만 허용한다.

### 5.3 기존 네이버 발송처리 연결

기존 네이버 발송처리는 `productOrderId`와 우체국 등기번호를 사용한다. 우체국 접수 성공 후 재확인된 `regiNo`만 기존 발송 후보 레코드에 넣는다.

- 하나의 주문의 다상품은 현재처럼 동일 운송장 1개라는 가정을 유지한다.
- 분할배송은 이 계획의 범위 밖이며, 자동 접수 대상에서 제외하거나 사용자 확인을 요구한다.
- 네이버 실제 발송처리는 상태를 되돌리기 어려우므로, 우체국 접수·인쇄 검증이 끝난 건에 대해서만 명시적 사용자 확인 후 호출한다.

## 6. 상태 모델

각 주문 또는 묶음의 우체국 처리 상태를 로컬 이력에 저장한다.

```text
접수대기
  → 접수요청중
  → 접수응답수신
  → 접수확인완료 (GetResInfo + regiNo)
  → 인쇄대기
  → 우체국인쇄요청됨
  → PC인쇄명령완료
  → 네이버발송대기
  → 네이버발송완료

접수요청중/접수응답수신/인쇄대기/우체국인쇄요청됨/PC인쇄명령완료
  → 실패 또는 사용자취소
```

`우체국인쇄요청됨`은 계약고객 시스템 팝업의 빨간 `인쇄` 버튼을 클릭해 OZ Report Viewer가 열렸다는 뜻이다. 이는 실제 종이 출력 성공을 보장하지 않는다.

## 7. API 처리 흐름

### 7.1 사전 검증

1. 로컬 설정에 인증키·보안키·고객번호·승인번호·공급지 코드가 모두 있는지 검사한다.
2. 고객번호·승인번호·공급지 조회 API로 계약 정보가 유효한지 검사한다.
3. 선택 주문별 필수 배송 정보와 상품 정보를 검사한다.
4. 접수 이력과 주문번호를 대조해 중복 접수를 차단한다.
5. 오류가 있는 행은 이유와 입력값의 항목명만 보여 주고, 유효한 행만 접수 후보로 만든다.

### 7.2 테스트 접수

실운영 전에 `testYn=Y`로 1건을 접수한다.

- SEED128 암호화가 우체국 서버와 호환되는지 확인한다.
- 성공 XML에 `reqNo`, `resNo`, `regiNo`가 있는지 확인한다.
- `GetResInfo` 결과가 같은 `regiNo`를 반환하는지 확인한다.
- 테스트 신청이 운송장출력 화면에 표시되는지와 출력 가능한지 확인한다.

테스트와 실접수의 표시·출력 동작이 다를 경우, 실발송 가능한 1건을 별도 사용자 확인 후 최소 범위로 검증한다.

### 7.3 실접수

1. 주문별 평문 파라미터를 UTF-8로 만든다.
2. 접수용 보안키로 SEED128 암호화해 `regData`를 만든다.
3. `InsertOrder`를 호출한다.
4. XML 성공 여부와 필수 결과값을 파싱한다.
5. 즉시 `GetResInfo`를 호출해 최종 등록 상태와 등기번호를 재확인한다.
6. 성공 건과 실패 건을 분리해 화면·로그·로컬 이력에 기록한다.

오류 XML은 오류코드·사용자에게 보여 줄 메시지·주문 식별자만 기록하며 주소·전화번호·키·암호화 데이터 전문은 로그에 남기지 않는다.

### 7.4 접수 취소

취소는 다음 조건에서만 제공한다.

- 해당 건이 OpenAPI로 접수된 이력이 있다.
- 우체국 집하완료 전이다.
- 사용자가 주문번호·등기번호·취소 사유를 확인했다.

취소 시 `reqNo`, `resNo`, `regiNo`를 이용해 `GetResCancelCmd`를 호출한다. 예약취소 후 등기번호가 변경될 수 있으므로, 기존 등기번호의 네이버 발송처리는 자동으로 하지 않는다.

## 8. 운송장 출력 자동화

### 8.1 대상 선정

계약고객 시스템의 `계약소포 > 운송장출력`에서 다음 조건을 적용한다.

- 검색일자: 접수일(기본 오늘)
- 발송지: 계약 설정의 발송지
- 출력대상: `신규출력`
- 필요 시 주문접수처명 등 추가 필터

`신규출력`은 이미 출력 처리된 건을 제외하므로 다건 출력에 적합하다. 그러나 다른 PC 또는 다른 작업자의 미출력 건도 포함될 수 있다.

자동화는 조회 후 다음을 반드시 대조한다.

| 조건 | 처리 |
| --- | --- |
| 조회된 신규출력 목록이 이번 실행의 접수 등기번호 목록과 정확히 일치 | 전체 선택 후 일괄 인쇄 진행 |
| 조회 목록에 예상하지 않은 등기번호가 포함 | 자동 인쇄 중단, 목록·건수 표시 후 사용자 확인 |
| 이번 실행 등기번호가 누락 | 자동 인쇄 중단, 접수 조회·날짜·발송지 조건 확인 |

### 8.2 실제 UI 흐름

1. 신규출력 조회 결과에서 대상 행을 선택한다.
2. `운송장출력` 버튼을 누른다.
3. 운송장출력 팝업에서 현재 사용하는 양식과 발송지 정보를 확인한다.
4. 팝업의 `인쇄`를 누른다.
5. OZ Report Viewer가 열렸는지와 예상 페이지 수를 확인한다.
6. 뷰어의 프린터 아이콘을 누른다.
7. 프린터 `Xprinter XP-DT108B`와 인쇄할 용지 `우체국`을 선택한다.
8. 최종 `확인`을 눌러 Windows 인쇄 명령을 보낸다.

웹 페이지와 OZ Report Viewer, Windows 인쇄 대화상자는 별도 프로그램이므로 Windows UI 자동화 도구를 사용한다. 창 제목·프린터명·용지명이 예상과 다르면 즉시 중단하고 화면에 조치 방법을 보여 준다.

### 8.3 출력 상태와 재출력

계약고객 시스템이 출력여부를 언제 변경하는지는 실제 테스트로 확정한다. 가장 가능성이 높은 시점은 운송장출력 팝업의 `인쇄` 클릭 시점이며, 이 경우 OZ Viewer 또는 프린터에서 실패해도 `신규출력`에서 사라질 수 있다.

확인 시험:

1. 테스트용 신규출력 1건을 준비한다.
2. 계약고객 시스템 팝업에서 `인쇄`를 눌러 OZ Viewer를 연다.
3. Windows 프린터 대화상자에서는 취소한다.
4. 운송장출력 목록을 새로 조회해 해당 건의 출력여부와 신규출력 노출 여부를 확인한다.

재출력은 `전체`에서 **특정 등기번호만** 검색·선택하고, 재출력 경고와 사용자 확인 후 실행한다. 신규출력 전체를 재출력 대상으로 사용하지 않는다.

## 9. 보안과 설정

### 9.1 비밀값

다음 값은 Git, 코드, 문서, 스크린샷, 콘솔 로그, 일반 업무 시트에 저장하지 않는다.

- 우체국 API 인증키
- 우체국 접수용 보안키
- 네이버 API 비밀값
- 암호화 전·후의 실제 `regData`

사용자 지시에 따라 기존 Google Sheets의 비공개 `설정` 탭(`키`, `값`)에서 읽는다. 같은 설정 탭에 접근 가능한 직원은 값도 볼 수 있으므로, 해당 접근 권한이 계약소포 접수 권한과 일치하는지 운영자가 관리한다.

### 9.2 개인정보와 로그

- 화면에는 발송에 필요한 수취인 정보를 보여 줄 수 있으나, 오류 로그에는 주문번호·등기번호·오류코드 중심으로 남긴다.
- 주소·전화번호는 필요 시 일부 마스킹한다.
- 접수 응답 XML의 원문 보관이 필요하면 접근 권한이 제한된 로컬 경로에만 보관하고, 기본값은 요약 저장으로 한다.

## 10. 구현 단계

### 1단계: API 기반과 설정

- 우체국 API 클라이언트, XML 파서, 오류 모델 작성
- 제공된 Java/PHP 예제를 기준으로 SEED128 암호화 호환 구현
- 로컬 비밀 설정 읽기와 마스킹된 설정 상태 표시
- 고객번호·승인번호·공급지 조회 진단 버튼

완료 기준: 실제 키 없이도 단위 테스트 가능하고, 실제 키가 있는 PC에서 계약 정보 조회가 성공한다.

### 2단계: 테스트 접수와 결과 이력

- 주문 데이터에서 접수 요청값 생성
- `testYn=Y` 단건 접수·결과 재조회
- 접수 결과 이력과 중복 차단 저장
- 오류별 사용자 메시지·콘솔 로그

완료 기준: 테스트 1건에서 `regiNo`를 얻고 재조회 결과가 일치한다.

### 3단계: 실접수 UX

- 선택 주문 다건 접수
- 접수 전 확인 창과 성공·실패 요약
- 취소 기능과 안전 확인
- 기존 네이버 발송 후보와 등기번호 연결

완료 기준: 실발송 가능한 1건을 명시적 사용자 확인 후 접수하고, 중복접수 없이 등기번호가 저장된다.

### 4단계: 인쇄 조사와 자동화 프로토타입

- `printYn` 값별 운송장출력 목록·출력 동작 검증
- 출력여부 전환 시점 확인
- 용지 `우체국` 설정의 지속 여부 확인
- 단건 운송장을 대상으로 웹·OZ Viewer·Windows 인쇄창 자동화

완료 기준: 테스트 1건에서 예상 프린터와 용지로 인쇄 명령이 전달되고, 불일치 시 안전하게 중단한다.

### 5단계: 다건 인쇄와 통합

- 오늘·발송지·신규출력 목록 조회
- 이번 실행 접수 등기번호 목록과 대조
- 일치 건만 일괄 출력
- 재출력 경로와 인쇄 상태 로그
- 인쇄 확인 후 네이버 발송처리 연결

완료 기준: 2~3건을 접수·일괄 인쇄하고, 각 등기번호가 올바른 주문의 네이버 발송 후보에 연결된다.

### 6단계: 제한 운영

- 초기는 `접수 자동 + 인쇄 직전 사용자 확인`으로 운영
- 오류·재출력·다른 PC의 미출력 혼입 사례를 기록
- 안정성 확인 후 최종 인쇄 확인까지 자동화 여부 결정
