## 1. 목표

`easy-fulfill`에 **문서 만들기** 상위 탭을 마지막에 추가한다. 직원은 견적서와 거래명세서를 각각 독립적으로 작성할 수 있고, 동일 프로그램의 기존 네이버 커머스API 인증정보를 이용해 스마트스토어 상품명과 가격을 기준값으로 조회할 수 있다.

문서 생성의 필수 경로는 수동 입력이다. 네이버 조회는 입력 편의를 위한 보조 기능이며, 인증·네트워크·API 오류가 발생해도 수동으로 계속 작성할 수 있어야 한다.

### 1.1 1차 구현 범위

- 견적서와 거래명세서의 독립 작성
- 직거래 할인, 배송비, 공급가액, 부가세 자동 계산
- 짧은 키워드로 스마트스토어 상품 찾기 및 기준가격 불러오기
- 문서용 상품명·규격·가격의 자유로운 수동 입력 및 수정
- 기존 엑셀 양식을 유지한 `.xlsx` 생성
- 같은 엑셀 양식을 Excel 인쇄 설정 그대로 `.pdf` 출력
- 기본 품목 행을 초과하면 행 자동 추가
- 생성 전 금액 명세 확인
- 기존 `output/` 폴더에 결과 저장

### 1.2 1차 구현에서 제외

- 견적서를 저장했다가 거래명세서로 전환하는 이력 기능
- 고객·문서 데이터베이스
- 전자결재, 세금계산서, 이메일 발송
- AI를 이용한 상품명 자동 축약
- 문서용 상품명 축약 규칙의 공용 저장·강제 적용

제외 기능은 실제 운영 필요가 확인될 때 추가한다.

## 2. 확정 업무 규칙

### 2.1 할인 판정 기준

결제 방법은 견적서 표기용으로 선택한다. 선택값은 할인·배송비 계산에 영향을 주지 않으며 스마트스토어 가격은 기준가격을 찾기 위한 참고값이다.

할인 구간은 **배송비를 제외한 할인 전 품목 합계**로 판정한다. 금액은 모두 부가세 포함 기준단가 기준이다. 수량 기준은 사용하지 않는다.

| 할인 전 품목 합계 | 할인율 | 배송비 |
|---:|---:|---:|
| 100,000원 이하 | 0% | 3,000원 |
| 100,000원 초과 ~ 2,000,000원 이하 | 5% | 없음 |
| 2,000,000원 초과 ~ 5,000,000원 이하 | 10% | 없음 |
| 5,000,000원 초과 | 자동 계산하지 않음 | 별도 협의 |

경계값은 다음과 같이 고정한다.

- 100,000원: 0% 할인 + 배송비 3,000원
- 100,001원: 5% 할인
- 2,000,000원: 5% 할인
- 2,000,001원: 10% 할인
- 5,000,000원: 10% 할인
- 5,000,001원: 별도 협의

### 2.2 품목별 금액 계산

금액 계산에는 이진 부동소수점 `float`를 사용하지 않고 Python `Decimal`과 `ROUND_HALF_UP`을 사용한다. 입력 가격도 문자열에서 바로 `Decimal`로 변환한다.

품목별 계산 순서는 다음과 같다.

```text
할인 전 품목 합계 = Σ(부가세 포함 기준단가 × 수량)
할인율 = 할인 전 품목 합계로 결정
할인 후 부가세 포함 단가 = 원 단위 반올림(기준단가 × (1 - 할인율))
공급 단가 = 원 단위 반올림(할인 후 부가세 포함 단가 ÷ 1.1)
세액 단가 = 할인 후 부가세 포함 단가 - 공급 단가
품목 공급가액 = 공급 단가 × 수량
품목 세액 = 세액 단가 × 수량
품목 합계 = 품목 공급가액 + 품목 세액
```

예: 기준단가 10,000원인 상품 400개를 구매하는 경우

```text
할인 전 품목 합계: 4,000,000원 → 10% 할인
할인 후 단가: 9,000원
공급 단가: 8,182원
세액 단가: 818원
공급가액: 3,272,800원
세액: 327,200원
최종 품목 합계: 3,600,000원
```

엑셀에는 계산 결과를 정수 값으로 기록한다. 기존 양식의 `/ 1.1` 수식은 사용하지 않아 `45,299.999...` 같은 표시 오차와 Excel 재계산 환경 차이를 없앤다.

### 2.3 배송비

- 할인 전 품목 합계가 100,000원 이하일 때만 배송비 3,000원을 추가한다.
- 100,000원 초과면 판매자 부담이며 문서에 배송비 행을 만들지 않는다.
- 배송비는 부가세 포함 금액으로 취급한다.
- 배송비 3,000원은 공급가액 2,727원, 세액 273원으로 기록한다.

### 2.4 5백만 원 초과

자동 할인율을 정하지 않는다. UI에 `별도 협의 대상`을 표시하고 문서 생성을 막는다. 협의 후에는 직원이 품목별 부가세 포함 단가를 수동으로 수정하고 `협의 완료`를 확인해야 생성할 수 있게 한다. 임의 할인율을 프로그램이 추정하지 않는다.

### 2.5 문서별 추가 규칙

- 견적서의 결제 방법은 `직거래`, `네이버`, `쿠팡`, `G마켓`, `옥션`, `11번가` 중 선택한다.
- 문서에는 각각 `직접 거래`, `네이버 스토어 거래`, `쿠팡 스토어 거래`, `G마켓 거래`, `옥션 거래`, `11번가 거래`로 기록한다.
- 할인율은 품목별 금액 계산에 적용하되 견적서에는 할인 행 자체를 표시하지 않는다.
- 스마트스토어의 긴 상품명은 API 원문 상품명으로 보존해 불러오되, 문서용 상품명과 규격은 사용자가 수정할 수 있게 한다.
- 견적서와 거래명세서는 서로 변환하거나 의존하지 않고 각각 생성한다.

## 3. 사용자 화면

상위 탭 순서는 다음을 기준으로 한다.

```text
주문발송 | 배송추적 | DB동기화 | 환경설정 | 관리자 | 단건 송장 | 문서 만들기
```

새 탭 내부 구성은 한 화면에서 위에서 아래로 진행한다.

1. 문서 종류: `견적서` 또는 `거래명세서`
2. 기본정보: 결제 방법, 소속명, 성명, 거래일자
3. 품목 표: 상태, API 상품명, 문서용 상품명, 규격, 수량, VAT포함 단가
4. 계산 요약: 할인 전 합계, 할인율, 할인액, 공급가액, 세액, 배송비, 최종 합계
5. 작업 버튼: 품목 추가/삭제, 상품 찾기, 초기화, 문서 생성, PDF로 출력

### 3.1 입력 검증

- 소속명, 성명, 거래일자는 필수다.
- 품목은 최소 1개이며 상품명, 1원 이상의 단가, 1개 이상의 수량이 필요하다.
- 숫자 입력에는 음수, 소수 수량, 빈 문자열을 허용하지 않는다.
- VAT포함 단가는 입력 완료 후 천 단위 콤마로 표시한다.
- 상태는 처음부터 직접 입력한 행은 `수동`, API 원본 적용 행은 `자동`, API 적용 후 문서용 상품명·규격·가격을 바꾼 행은 `수정`으로 표시한다.
- 생성 전 확인창에 모든 품목과 최종 금액을 표시한다.

## 5. 스마트스토어 기준가격과 상품명 찾기

문서 발행자가 스마트스토어의 SEO 상품명을 정확히 기억하거나 그대로 문서에 써야 하는 구조로 만들지 않는다. 상품 선택과 문서 표기를 아래처럼 분리한다.

```text
발행자가 상품명 또는 짧은 키워드 입력
→ API로 상품명·가격 후보 검색
→ 후보 목록에서 제품명과 가격을 확인하고 실제 상품 선택
→ API 제품명과 기준가격을 품목 행에 적용
→ 발행자가 문서용 상품명·규격·단가를 최종 수정
→ 수정된 값으로 문서 생성
```

### 5.1 검색 방식

- 네이버 커머스API의 공식 상품 목록 조회 API를 사용한다. 공식 문서: <https://apicenter.commerce.naver.com/docs/commerce-api/current/search-product>
- 기존 `naver_commerce.get_access_token()`과 설정 탭의 `naver_client_id`, `naver_client_secret`을 재사용한다.
- 검색창은 정확한 전체 상품명이 아니라 `stm32`, `h7`, `개발보드` 같은 단어 일부를 받는다.
- `상품 찾기`를 누르면 검색어로 API 상품 목록을 백그라운드 조회한다. 조회 결과가 넓으면 해당 실행 동안 메모리에 둔 결과에서 공백·대소문자를 무시한 포함 검색으로 다시 좁힌다.
- 결과에는 스마트스토어 원문 상품명, 상품번호, 기준가격을 보여준다.
- 발행자는 제품명과 가격을 확인한 뒤 `적용`을 눌러야 품목 행에 반영된다. 검색 결과를 한 번 클릭한 것만으로는 기존 입력값을 덮어쓰지 않는다.
- API 응답의 `discountedPrice`가 0보다 크면 이를 기준가격으로 적용하고, 아니면 `salePrice`를 적용한다.

### 5.2 문서용 이름은 사람의 최종 판단

- 적용 직후에는 원문 상품명을 `API 상품명`에 보존하고, 같은 값으로 `문서용 상품명`을 채운다.
- `문서용 상품명`과 `규격`은 별도 편집 칸이며 자동 축약하지 않는다.
- 수정하지 않으면 API 원문 상품명이 그대로 문서에 출력된다. 발행자는 매 문서에서 자유롭게 축약·수정할 수 있다.
- 예: `STM32H723 교육용 개발보드 STM32H7-GFX V1 TouchGFX`를 `STM32H7-GFX 개발 보드`, 규격을 `Ver1`로 직접 정정한다.
- 문서에는 문서용 상품명과 규격만 출력한다. API 상품명은 발행 화면의 확인용 정보로만 남긴다.
- API 적용 후 가격·문서용 이름·규격을 수정하면 해당 행에 `수정`을 표시한다.

자동 축약이나 공용 별칭 사전은 현재 제외한다. 동일 상품의 표기 통일이 실제로 필요해지면, 그때 담당자가 관리하는 별칭표를 별도 기능으로 추가한다.

### 5.3 API 실패 시 동작

- 인증 실패, 시간 초과, 검색 결과 없음은 해당 탭 안에서 안내한다.
- 기존에 입력한 품목 행은 지우지 않는다.
- API 상품명 없이 문서용 상품명·규격·VAT 포함 단가를 수동 입력해 계속 생성할 수 있다.

## 6. 엑셀 템플릿 처리

### 6.1 템플릿 준비

제공된 실제 작성본을 그대로 사용하지 않는다. 다음 작업을 거쳐 자동화용 템플릿을 저장소에 추가한다.

- 고객명, 소속, 날짜, 품목, 금액 등 샘플값 제거
- 공급자 상호, 등록번호, 주소, 전화번호, 대표자 정보 확인
- 견적서의 결제 방법 행에는 화면에서 선택한 표기값이 기록되도록 정리
- 로고, 병합 셀, 열 너비, 행 높이, 테두리, 글꼴, 인쇄 여백 유지
- 원본 파일과 정리된 템플릿을 Excel에서 나란히 확인

완성 고객 문서와 `output/` 결과물은 Git에 넣지 않는다. 저장소에는 개인정보가 없는 템플릿만 커밋한다.

### 6.2 품목 행 추가

- 견적서 기본 품목 행: 7개
- 거래명세서 기본 품목 행: 6개
- 기본 행을 초과하면 합계 행 바로 위에 필요한 수만큼 삽입한다.
- 기준 품목 행의 병합 범위, 높이, 테두리, 정렬, 표시 형식을 복제한다.
- `openpyxl.insert_rows()`가 수식·병합·인쇄영역을 완전히 보정한다고 가정하지 않고, 삽입 후 합계 위치와 병합 범위를 명시적으로 다시 설정한다.
- 모든 금액과 합계는 앱에서 계산한 정수 값으로 기록한다.
- 품목 증가 후 인쇄 영역을 다시 지정한다.
- 기본 행 수 이내이면 현재 1페이지 출력을 유지한다.
- 행 추가 시 가로 1페이지 맞춤은 유지하고 세로는 여러 페이지를 허용해 글자가 과도하게 축소되지 않게 한다.

### 6.3 출력 파일명

```text
output/견적서_소속명_성명_YYYYMMDD_HHMMSS.xlsx
output/거래명세서_소속명_성명_YYYYMMDD_HHMMSS.xlsx
output/견적서_소속명_성명_YYYYMMDD_HHMMSS.pdf
output/거래명세서_소속명_성명_YYYYMMDD_HHMMSS.pdf
```

Windows 파일명에 사용할 수 없는 문자는 제거한다. 같은 이름이 있어도 타임스탬프로 덮어쓰기를 방지한다.

## 7. 구현 순서

### 1단계: 템플릿 정리와 셀 매핑

- 제공 파일을 개인정보 없는 템플릿으로 정리한다.
- 각 입력값과 출력값의 셀 좌표를 표로 확정한다.
- `openpyxl`로 불러와 그대로 다시 저장한 왕복 파일에서 로고·병합·인쇄 설정 보존 여부를 확인한다.
- 표준 이미지나 서식이 손실되는 경우에만 Excel COM 방식 사용을 재검토한다.

완료 조건: 내용이 빈 템플릿 2개가 Excel에서 원본과 동일한 형태로 열린다.

### 2단계: 계산 엔진

- 거래 및 품목 입력 구조를 간단한 `dataclass`로 정의한다.
- 할인 구간, 품목별 단가, 배송비, 공급가액, 세액, 합계를 순수 함수로 구현한다.
- 계산 함수는 Qt와 Excel을 import하지 않는다.
- 경계값 테스트를 먼저 통과시킨다.

완료 조건: 아래 8절의 계산 검사가 모두 통과한다.

### 3단계: 엑셀 생성

- 템플릿을 `output/`으로 복사한 뒤 값만 채운다.
- 샘플 잔여값이 없는지 확인한다.
- 품목 행 초과 시 행을 확장한다.
- 생성 파일을 다시 열어 값, 병합, 인쇄영역을 검사한다.

완료 조건: 견적서 8품목과 거래명세서 7품목이 잘리지 않고 생성된다.

### 3-1단계: PDF 출력

- `PDF로 출력`은 XLSX를 먼저 생성한 뒤 Excel COM의 PDF 내보내기를 실행한다.
- PDF는 XLSX와 같은 이름·같은 `output/` 폴더에 저장한다.
- Excel 또는 PDF 변환이 실패해도 먼저 만든 XLSX는 유지하고 오류를 안내한다.

### 4단계: 수동 작성 UI

- 새 상위 탭과 위젯을 장착한다.
- 수동 품목 입력, 계산 요약, 생성 확인창을 구현한다.
- 문서 종류 변경 시 입력값은 유지하고 문서별 필수항목만 갱신한다.
- 생성 실패가 기존 주문·배송 탭에 영향을 주지 않도록 예외를 해당 위젯에서 처리한다.

완료 조건: 네트워크가 없는 PC에서도 두 문서를 생성할 수 있다.

### 5단계: 스마트스토어 상품 찾기

- `naver_commerce.py`에 판매 중 상품 목록 조회 함수만 추가한다.
- 기존 공유 인증정보와 오류 처리 함수를 재사용한다.
- 짧은 키워드로 실행 중 메모리의 상품 목록을 필터링한다.
- 검색 결과에서 제품명·가격을 확인하고 적용하면 API 상품명과 기준가격을 품목 행에 채운다.
- 결과를 채운 뒤에도 문서용 상품명·규격·가격을 수정할 수 있게 한다.

완료 조건: API 성공·인증 실패·시간 초과·결과 없음 모두 UI가 멈추지 않고 수동 입력이 유지된다.

### 6단계: 통합 검증과 배포

- 기존 주문·배송, 단건 송장, 환경설정 탭의 회귀 동작을 확인한다.
- 실제 과거 거래 3~5건을 담당자의 수기 문서와 원 단위로 대조한다.
- 기능 브랜치에서 검증 후 `main`에 병합한다.
- 직원 공지 후 각 PC에서 SourceTree `Fetch → Pull`, `run.bat` 실행으로 배포한다.
- 안정 버전에 태그를 추가한다. 예: `v1.8.0-quotation-statement`.

## 9. 커밋 계획

작업 중 생성된 고객 문서와 테스트 출력물은 커밋하지 않는다. 구현 커밋은 다음처럼 검토 가능한 크기로 나눈다.

1. `docs: 견적서·거래명세서 자동화 계획 추가`
2. `feat(documents): 견적서·거래명세서 계산 및 템플릿 생성 추가`
3. `feat(ui): 문서 만들기 탭 추가`
4. `feat(naver): 스마트스토어 상품 가격 검색 연동`

실제 커밋 수와 메시지는 변경 범위와 저장소의 최신 관례를 다시 확인한 뒤 조정한다. 구현 완료 전에는 원격 푸시하지 않는다.

## 10. 완료 기준

- 직원이 기존 `easy-fulfill`에서 견적서와 거래명세서를 각각 작성할 수 있다.
- 네이버 API 없이도 모든 문서를 수동 작성할 수 있다.
- 확정 할인 경계값과 품목별 반올림이 자동 검사로 고정된다.
- 기본 행을 초과한 문서도 서식과 인쇄 가독성을 유지한다.
- 기존 주문발송, 배송추적, DB동기화, 환경설정, 관리자, 단건 송장의 주요 기능에 회귀가 없다.
- 출력 문서에 샘플 개인정보와 소수점 표시 오차가 없다.
- SourceTree Pull 후 기존 `run.bat` 실행 절차로 직원 PC에 배포할 수 있다.
